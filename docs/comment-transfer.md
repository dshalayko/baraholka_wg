# Перепубликация и перенос комментариев

При обновлении создаётся новый пост. Его ID и задание переноса сохраняются одной транзакцией с обновлением объявления. HTTP-запрос не ждёт копирования комментариев. В боте и мини-приложении показывается, что перенос продолжается.

Фоновый обработчик запускается в `main.py` и `webserver/app.py`. Оба процесса должны использовать одну БД и общий локальный каталог блокировок рядом с ней. Блокировки `flock` автоматически освобождаются при завершении процесса. Сессия Pyrogram также защищена общей блокировкой; сбор счётчиков не блокирует перенос, если сессия занята.

## Что сохраняется

- Вся доступная ветка, включая вложенные ответы. Если родитель уже удалён, ответ помещается под корень нового поста.
- Имя и ссылка на автора, исходная дата в часовом поясе Белграда. У новых копий отправителем остаётся служебный аккаунт.
- Текст и Telegram entities, включая форматирование, ссылки и упоминания. Длинные сообщения делятся по лимитам UTF-16 без разрыва символов.
- Фото, видео, GIF/animation, документы, аудио, голосовые, стикеры и видеокружки. Фото/видео/аудио/документы из альбома отправляются альбомом. Для стикера/кружка автор и дата идут отдельным сообщением.
- Метаданные исходного комментария хранятся отдельно. При следующей перепубликации подписи не наслаиваются, дополнительные части не превращаются в новые самостоятельные комментарии.

Старые копии, созданные прежним кодом, распознаются по прежней подписи только у служебного аккаунта. Исходную дату, которую старый код не сохранил, восстановить нельзя — это явно отмечается.

## Надёжность

`publication_jobs` хранит этап публикации: preparing, sending/uncertain, transfer, cleanup, done. `comment_copies`, `comment_operations` и `transferred_parts` сохраняют исходные данные, связи и прогресс каждого сообщения.

До отправки комментария сохраняются MTProto random_id. После потери ответа обработчик ищет уже отправленную копию по ссылке-маркеру на слове «Перенесено» и служебному отправителю. Для стикеров и кружков проверяются ответ на служебную подпись и идентификатор файла. Повторная отправка использует тот же random_id. Неполная доставка альбома или невозможность подтвердить результат блокирует удаление старого поста.

Ошибки не считаются успехом. Повтор начинается через 30 секунд, затем интервал увеличивается до часа; FloodWait учитывается отдельно. Неподдерживаемое вложение (например, опрос) оставляет перенос незавершённым и исходный пост на месте. Автоматические повторы не могут исправить постоянное отсутствие прав или добавить поддержку неизвестного типа — оператор должен устранить причину, видимую в журнале.

Пока задание активно, повтор публикации возвращает существующий новый пост. Изменение и удаление в API блокируются; удаление через старый бот также защищено. После завершения одинаковое повторное нажатие в пределах 60 секунд от начала публикации возвращает прежний результат. Более позднее осознанное поднятие объявления разрешено.

Перед удалением обработчик повторно читает ветку, ждёт минимум 10 секунд без обнаружения новых комментариев, снова читает её и проверяет наличие копий в Telegram. Если удаление не удалось, при повторе он опять проверяет комментарии, пока исходный корневой пост существует.

Telegram не предоставляет атомарной операции «запретить ответы и перенести ветку». Между последней проверкой и удалением остаётся небольшое окно гонки. При штатном автоудалении Telegram исходные посты и комментарии также могут исчезнуть независимо от бота. Полную гарантию против этих двух случаев дать нельзя. Журнал содержит снимки комментариев, полученные во время переноса; это не непрерывный архив всех обсуждений. Истёкшие ссылки на медиа обновляются из ещё доступного исходного сообщения; сами файлы локально не архивируются.

Реакции, оригинальные Telegram ID, права пользователя редактировать исходное сообщение и нативное авторство копий не переносятся. Правки/удаления оригинала после уже выполненного копирования не синхронизируются в копию.

## Неоднозначный результат публикации

Bot API не даёт ключа идемпотентности для отправки нового поста. Если процесс умер или ответ потерян после начала отправки и до записи ID, автоматическое повторение запрещено: оно могло бы создать дубликат. Объявление получает статус проверки администратором. Перенос комментариев через MTProto имеет отдельную защиту и обычно восстанавливается автоматически.

Команды выполняются в каталоге проекта с его обычной конфигурацией:

```sh
.venv/bin/python -B transfer_admin.py status
.venv/bin/python -B transfer_admin.py retry 123
```

Если новый пост действительно появился, оператор проверяет его содержимое и передаёт ID всего нового поста/альбома:

```sh
.venv/bin/python -B transfer_admin.py resolve 123 4567 4568
```

Команда проверит существование сообщений в настроенном канале, дату и полноту альбома, затем атомарно свяжет их с объявлением и продолжит перенос. Она не определяет по содержимому, то ли объявление выбрал оператор: это нужно проверить вручную. Параметры публикации, включая окончание аукциона, сохранены перед отправкой и восстанавливаются вместе с ID.

Только если оператор удостоверился, что новый пост **не отправлен**, можно сбросить неопределённую попытку:

```sh
.venv/bin/python -B transfer_admin.py reset-unsent 123 --confirmed-not-sent
```

Без такой проверки сброс может привести к дубликату.

## Запуск и проверки

Таблицы добавляются автоматически без изменения существующих объявлений. Для включения изменений нужно обновить код и перезапустить бот и веб-сервис. Старые задания, созданные до появления журнала, автоматически не восстанавливаются.

```sh
.venv/bin/python -B -m unittest discover -s tests -v
```

Тесты используют временную SQLite и имитацию Telegram. Проверяются дерево ответов, повторные публикации, потерянные ответы, частичный перенос, альбомы, длинный текст/emoji/entities, несколько поколений копий, вложения, поздние комментарии, повтор удаления, блокировки, FloodWait и реальные HTTP-обработчики с подменённым Telegram-клиентом. Они не отправляют сообщений в реальные чаты. Перед эксплуатацией желательно проверить цикл в отдельном тестовом канале с связанной группой и действующей userbot-сессией.
